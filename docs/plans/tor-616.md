# Tor back in Epic GUI Wallet 6.1.6: spec and tasks

Branch `feat/tor-616` (off `build/6.1.6-rc`), 2026-10-21. Builds on the research in [tor.md](tor.md) (19 Oct). Everything below was re-checked on 21 Oct against the epic-wallet `v4.1.0` source tag, the bundled `epic-wallet 4.1.0` binary and dist.torproject.org. Modern interface only (Classic is frozen).

## Goal

A wallet with Tor turned on can **receive** at its `.onion` address and **send** to another wallet's `.onion` address, reliably, on Linux and Windows. Tor stays off by default and out of a beginner's way, but it's easy to find in Settings › Receiving, on Receive, on Send and in Contacts.

**Out of scope:** node traffic over Tor (node checks, `post_tx`, the built-in node's p2p), Epicbox over Tor, bridges and pluggable transports, payment proofs (the GUI doesn't ask for them on any method), testing on macOS (the fetch script supports mac, but there are no mac builds in 6.1.6), Classic, and changes to epic-wallet's own code (they go to the maintainers as notes, see §8).

## 1. What changed since the 19 Oct research

| Finding (21 Oct) | How it was checked | Effect |
|---|---|---|
| **epic-wallet 4.1.0 writes the onion secret key in the wrong format.** `create_onion_service_sec_key_file` writes the 32-byte seed followed by the 32-byte public key. Tor expects the 64-byte *expanded* key (SHA-512 of the seed, clamped). So tor publishes a different address from the one the wallet shows | Spike: epic-wallet listener wrote `mk7ca5…luyd` (matching `epic-wallet address`). Tor loaded the same file as `3dsdhc…5yad`. After expanding the seed ourselves, tor published `mk7ca5…luyd` | This is a third reason why 4.x Tor never worked. The GUI expands the key itself (§4) |
| The node-secret leak in `post_tx_tor` is **fixed in 4.1.0**: `api_secret_for_request` returns `None` for `/v2/tor`. The result is still discarded, though (`let _res = …; Ok(())`) | `impls/src/node_clients/http.rs` L115-122, L222-230 | Still a reason to keep `use_tor_listener = false` in every long-running process |
| `owner_api` has no `--no_tor` flag and reads `use_tor_listener` from the same toml as the listener. Its Epicbox send (`api/src/owner.rs` L758-777) passes that `tor_config` on to the finalize step that calls `post_tx_tor` | source | The main toml must keep `use_tor_listener = false`. Only a one-shot key run gets `true` (§4) |
| `ensure_running` doesn't start tor when something already answers on `socks_proxy_addr`, and it still sets `TOR_MANAGER` | `tor_manager.rs` | We point it at our own tor, so it never starts one of its own |
| Latest stable: **tor 0.4.9.14**, **Tor Expert Bundle 15.0.25** (unchanged since 19 Oct; 16.0a14 is alpha) | torproject.org/download/tor, dist.torproject.org/torbrowser/ | Pin 15.0.25 |
| Signatures: `Good signature`. VALIDSIG primary key `EF6E 286D DA85 EA2A 4BA7 DE68 4E2C 6E87 9329 8290`, signing subkey `022D…07D9`. The key from WKD has subkeys expiring **2026-10-26** and 2028-11-28 | gpg with a scratch keyring over WKD | Pin the primary fingerprint, never a keyring file |
| Linux bundle: `tor` 3.6 MB plus `libssl.so.3`, `libcrypto.so.3` and `libevent-2.1.so.7` (10.5 MB). Needs `LD_LIBRARY_PATH`, the system libz and glibc ≥ 2.24. Windows: `tor.exe` 10.2 MB, self-contained | `tor --library-versions`: OpenSSL 3.5.9, libevent 2.1.13 | +~10.5 MB unpacked per platform |
| The bundle's `tor --version` says "This build of Tor is covered by the GNU General Public License" (built with GPL parts). Tor's own source is BSD-3 | run | We ship it as a separate program next to an Apache-2.0 app (aggregation), with its licence file and a link to the source |
| Arti 2.7.0 (1 Oct 2026) is a full client and can host onion services, but there are **no official binaries** yet and no C-tor ControlPort | arti README and CHANGELOG | Not now. Worth revisiting once official binaries exist |

### Spike (Linux, scratch dir, network on, throwaway mainnet wallet with no funds)

1. Our own tor: `SocksPort auto ExtendedErrors`, `ControlPort auto` with a cookie, `__OwningControllerProcess`.
2. `epic-wallet listen --method http` with `use_tor_listener = true` and `socks_proxy_addr` set to our SOCKS port. It wrote the keys in 0.9 s and started no tor of its own.
3. `ADD_ONION` with the expanded key.

Results:

- Bootstrap reached 100 % at 7.2 s.
- `HS_DESC UPLOADED` came at 10.9 s.
- `check_version` to our own onion over SOCKS answered in 9.4 s (`foreign_api_version 2`, slates V3/V2).
- A malformed onion fails at once with SOCKS `0xF6`.
- A valid but offline onion fails with `0xF0` only **after 120 s**, so we need our own shorter timeout.

The spike scripts are in the lead's scratch dir (deleted with it). The steps are reproduced in the unit tests and specs below.

## 2. Decisions (with the pick)

| # | Question | Options | Pick and why |
|---|---|---|---|
| D1 | Who runs tor | (a) epic-wallet `listen` starts tor from `tor/tor`; (b) **the GUI runs its own tor**; (c) a system tor | **(b)**. One tor per open wallet, started by the main process, on private `auto` ports, with a ControlPort. That gives real readiness (bootstrap events, `HS_DESC UPLOADED`), plain errors, retries, and cleanup (`__OwningControllerProcess`, `TAKEOWNERSHIP`). There's no clash with a system tor on 9050, Tor Browser on 9150 or the test port offsets. (a) is the design that failed: a thread that panics, a 20 s timeout, no status, a wrong key format |
| D2 | Sending to `.onion` | (a) epic-wallet's own `http`/`tor` sender from the owner API; (b) `ALL_PROXY` on the owner API; (c) **the GUI exchanges the slate over SOCKS** | **(c)**. `init_send_tx` with no `send_args`, then the GUI POSTs `check_version` and `receive_tx` to `http://<onion>/v2/foreign` through tor's SOCKS (main process), then `tx_lock_outputs`, `finalize_tx` and `post_tx` to the wallet's own node, exactly the order epic-wallet's `init_send_tx` uses. (a) can't work (no `TOR_MANAGER` in the owner API). (b) would also push node calls through Tor, and Cloudflare-fronted nodes block Tor exits. (c) never calls `post_tx_tor` and turns each failure into a plain message |
| D3 | The onion address | (a) a random key held by the GUI; (b) **the wallet-derived key** | **(b)**. It's the same address the CLI and older GUIs show, it's the wallet's payment-proof address, and it survives a restore from the phrase. The GUI shows it from `get_public_proof_address(0)`, converted to onion v3. The key file is made once per wallet by a one-shot epic-wallet run (§4), and the GUI fixes the key format when it loads it into tor |
| D4 | Bundling | Expert Bundle binaries committed to git / **fetched at build time** / built from source | **Fetched at build time.** Tor Expert Bundle 15.0.25 is pinned in `resources/tor/tor-bundle.json` (SHA-256 of each tarball and of each extracted file, plus the signing key's primary fingerprint). The release build on Linux also checks the GPG signature. Nothing goes into git |
| D5 | Scope of the setting | per app / **per wallet** | **Per wallet** (`tor_enabled` in the wallet's settings, default off), like `http_listener_autostart`. Each wallet's onion and tor data live in its own folder, and wallets don't share Tor guards |
| D6 | Tor and the HTTP listener | separate switches / **Tor brings the listener** | **While Tor is on, the GUI keeps the HTTP listener running** on 127.0.0.1 (Tor needs it). The HTTP row says "Used by Tor" and its Turn off is disabled |
| D7 | Where it shows | — | Settings › Receiving › Tor row (the "advanced" group at the bottom). Receive has a Tor row only while Tor is on. In Send, pasting an onion while Tor is off gives an inline "Turn on Tor" button. Contacts show the onion field when Tor is on or the contact already has an onion address. The sidebar hover card gets one Tor line while it's on. One Help topic |

**Needs the user's word:** nothing blocks. All the picks above go ahead unless the user says otherwise.

## 3. Bundling

- `resources/tor/tor-bundle.json` (committed):
  - `bundleVersion: "15.0.25"`, `tor: "0.4.9.14"`, `baseUrls: ["https://dist.torproject.org/torbrowser/", "https://archive.torproject.org/tor-package-archive/torbrowser/"]`, `signingKey: "EF6E286DDA85EA2A4BA7DE684E2C6E8793298290"`, `wkd: "torbrowser@torproject.org"`
  - per GUI platform (`linux`: `tor-expert-bundle-linux-x86_64-…`, `win`: `…-windows-x86_64-…`, `mac`: `…-macos-x86_64-…`, `macsilicon`: `…-macos-aarch64-…`): `tarball`, `sha256`, and `files: {name: sha256}` for exactly the files kept
  - linux: `tor`, `libssl.so.3`, `libcrypto.so.3`, `libevent-2.1.so.7`; win: `tor.exe`; mac and macsilicon: `tor`, `libevent-2.1.7.dylib`
  - plus `docs/tor.txt` → `LICENSE.tor.txt`
- `scripts/fetch-tor.mjs --platform linux,win|all [--gpg required|auto|skip] [--bump <bundleVersion>]`. Node 22, no new npm dependencies; `tar` from the system (bsdtar on Windows 10+).
  1. Download into a cache (`~/.cache/epic-gui-tor/<version>/`, or `%LOCALAPPDATA%` on Windows), reusing it when the SHA-256 still matches.
  2. Check the tarball's SHA-256 against the json. On a mismatch, delete the download and exit non-zero.
  3. GPG: create a temporary `GNUPGHOME`, run `gpg --auto-key-locate nodefault,wkd --locate-keys <wkd>`, then `gpg --status-fd 1 --verify x.asc x`. It must print `VALIDSIG` whose **primary-key field equals `signingKey`**. `required` fails without gpg; `auto` (the default) warns and goes on with SHA-256 only.
  4. Extract into a fresh temp dir, copy only the listed files to `resources/bin/<plat>/tor-bundle/` with mode 0755, check each one's SHA-256 against `files`, and write `VERSION` (bundle and tor version).
  5. `--bump`: fetch `sha256sums-signed-build.txt` and its `.asc`, require a good GPG signature, then rewrite the json's hashes, extracted-file hashes included. This is the only way the pins change.
- The directory is `tor-bundle/`, **not** `tor/`. epic-wallet 4.x looks for `<exe dir>/tor/tor` itself, so it can never find, and start, an unmanaged tor.
- `vue.config.js` already copies `resources/bin/<plat>/**`. Check that `tor-bundle/` lands in the package; if not, add it.
- `.gitignore`: `resources/bin/*/tor-bundle/`. `package.json` gets the script `"fetch-tor": "node scripts/fetch-tor.mjs"`.
- `scripts/release.sh`:
  - after `npm ci`, run `node scripts/fetch-tor.mjs --platform linux,win --gpg required`
  - copy the verified `resources/bin/win/tor-bundle/` to the Windows build dir with `scp` before `build.cmd`, so Windows doesn't need gpg
  - record the tor version and hashes in the manifest
- `scripts/test-gate-windows.sh` (rig builds) does the same copy.
- `scripts/package-check.js`: the rule `no-tor` becomes `tor-bundle`:
  - the package must contain exactly the listed files, only in `bin/<plat>/tor-bundle/`, each with its pinned SHA-256
  - any other tor file anywhere fails: `tor-gencert*`, `pluggable_transports`, the old DLLs, `torrc*`, `geoip*`, and `tor/tor` next to epic-wallet
  - raise `scripts/package-budgets.json` by the measured size only
- Dev runs without a fetched bundle still work: the Tor row then says "Tor isn't included in this build" (`missing`).

## 4. Process management (main process)

New modules, plain ESM with injected `spawn`/`net`/`fs` so they can be unit-tested, following `shared/processOwnership.js` and `shared/ptyHost.js`:

- `src/shared/onion.js`
  - `onionFromPubkeyHex(hex)`: base32(pubkey ‖ sha3-256(".onion checksum" ‖ pubkey ‖ 0x03)[0..2] ‖ 0x03)
  - `parseOnion(text)` → `{host, valid, reason}`: accepts the bare 56-character name, with or without `.onion`, `http://`, `:80` or a trailing `/`, and checks the checksum and version
  - `expandSeed(seed32)`: SHA-512, then clamp. No secret ever goes into a log
- `src/shared/torControl.js`: a minimal control-port client.
  - Commands: `AUTHENTICATE <cookie hex>`, `TAKEOWNERSHIP`, `RESETCONF __OwningControllerProcess`, `GETINFO net/listeners/socks`, `GETINFO status/bootstrap-phase`, `SETEVENTS STATUS_CLIENT STATUS_GENERAL HS_DESC`, `ADD_ONION ED25519-V3:<b64> Port=80,127.0.0.1:<listener>` (with `Flags=DiscardPK`, so the key isn't echoed back), `DEL_ONION`, `SIGNAL SHUTDOWN`
  - It parses `250`/`650` replies, multi-line replies included
- `src/shared/torManager.js`: the per-wallet state machine and torrc builder.
  - torrc is written to `<configDir>/tor/torrc`, with tor's data in `<configDir>/tor/data` (0700):
    ```
    SocksPort auto ExtendedErrors IsolateSOCKSAuth
    ControlPort auto
    ControlPortWriteToFile <configDir>/tor/control.txt
    CookieAuthentication 1
    CookieAuthFile <configDir>/tor/control.cookie
    DataDirectory <configDir>/tor/data
    __OwningControllerProcess <main pid>
    Log notice stdout
    AvoidDiskWrites 1
    ```
  - Started as `tor -f <torrc> --defaults-torrc <empty file>`, with `LD_LIBRARY_PATH=<tor-bundle>` on Linux and `windowsHide` on Windows. No shell, no pty.
  - States: `off → starting (progress 0-100, phase tag) → publishing → ready`, with `failed{error, detail}` from any of them.
    - **ready** = bootstrap 100 % and the first `HS_DESC UPLOADED` for our service ID. Sending only needs bootstrap 100 %, receiving needs ready.
    - Republishing is tor's own job. A later `HS_DESC FAILED` on every HSDir only logs; it doesn't fail the state.
  - Errors (`error` codes for the UI):
    - `missing`: no binary
    - `start`: tor exited before the control file appeared; `detail` = tor's last `[err]`/`[warn]` line
    - `network`: progress stuck for 60 s, or no 100 % after 120 s; restarts with backoff (5 s, 30 s, 2 min)
    - `clock`: a `CLOCK_SKEW` event
    - `keys`: key creation failed
    - `listener`: the HTTP listener isn't running
    - `node` (6.1.6 Tor round): the listener can't start because the node doesn't answer (epic-wallet `listen` refuses: "node not synced"). Tor starts anyway with `waitListener`: it bootstraps (sending works; with no network at all this ends in `network`, not here), shows `node` once bootstrapped, and adds the onion when the listener port answers (checked every 3 s). The page tries the listener again every 30 s and when the node poll turns synced (walletService.retryTorListener)
  - Stop:
    - `DEL_ONION` and `SIGNAL SHUTDOWN` over control, then a kill after 5 s
    - on lock, wallet switch, Tor off, quit (`shutdown.js`) and when the wallet is removed
    - if the app crashes, tor exits by itself because its owning process is gone
- `processOwnership.js`: record our tor by pid with role `tor` (args `-f <configDir>/tor/torrc`), so a leftover one is found at start and on wallet removal. Keep the legacy `wallet_tor/torrc` detection. `BIN_NAME` allows `tor(.exe)` again, but only for this role.
- `background.js` IPC. Every handler checks `fromAppWindow(event)`; add the channels to the contract test lists.
  - `tor-start {walletId}`: config and data dirs come from the main process's own wallet record, never from paths the renderer passes
  - `tor-stop`
  - `tor-status` (an event pushed to the window)
  - `tor-foreign {onion, method: 'check_version'|'receive_tx', params}`:
    - target must pass `parseOnion`; the path is fixed at `/v2/foreign` on port 80
    - body ≤ 1 MB, response ≤ 4 MB
    - timeouts: 72 s to connect (tor needs up to 120 s to say "not found", which is too long to wait), 120 s for the reply. A connect timeout of check_version is tried once more on a new circuit (another isolation name): the first circuit to a fresh onion took 35–75+ s in the Tor round, the next one 1.4 s
    - a SOCKS username unique to each send (stream isolation)
    - answers `{ok, result}` or `{ok: false, code, detail}`

### The onion key (one-shot, per wallet, only when missing)

The key's seed comes only from epic-wallet (it is derived from the wallet key). When `<dataDir>/wallet_tor/onion_service_addresses/<onion>/hs_ed25519_secret_key` is missing (96 bytes, header `== ed25519v1-secret: type0 ==`), and `<onion>` is the address from `get_public_proof_address(0)`:

1. Render `<configDir>/tor-keys/epic-wallet.toml` with `renderWalletToml`, changing only `[tor] use_tor_listener = true`, `socks_proxy_addr = "127.0.0.1:<our SOCKS port>"`, and a free `api_listen_port`.
2. Start `epic-wallet --offline_mode -t <dataDir> -c <configDir>/tor-keys listen --method http` on the pty host, as the new kind `torkeys` in `walletArgs.PTY_COMMANDS`. The pty host answers the password prompt as usual.
3. Once the key file for `<onion>` exists, check that its public-key half matches `<onion>`, then stop the process (it never gets past its offline start). Allow 30 s, then fail with error `keys`.

After that, the GUI reads the seed (bytes 32-64), expands it in memory and calls `ADD_ONION`. It never writes the expanded key and never logs either key. The main toml keeps `use_tor_listener = false`, and every long-running listener keeps `--no_tor`.

## 5. Receiving and sending

**Receiving.**

- Tor on and wallet unlocked:
  1. Start tor and wait for the SOCKS port.
  2. Make sure the onion key exists.
  3. Make sure the HTTP listener is running (on 127.0.0.1:3415 or its test offset).
  4. Call `ADD_ONION` for port 80 → the listener port.
  5. Show ready on the first `HS_DESC UPLOADED`.
- If the listener stops, the state becomes `failed: listener`, with a Retry that restarts it.

**Sending** (`walletService.sendOverTor(txData, onion, onStep)`):

1. `parseOnion`. Invalid → `invalid`.
2. Tor not ready → `tor_off` (Send shows the Turn on Tor button) or wait for bootstrap with progress.
3. `tor-foreign check_version`.
   - Needs `foreign_api_version ≥ 2`. Pick V3 if offered, otherwise V2, as `adapters/http.rs` does.
   - The GUI never asks for a payment proof, so V2 is fine.
4. `init_send_tx` without `send_args` (as the file send does), with `target_slate_version` set to the version from step 3.
5. `tor-foreign receive_tx [slate, null, null, null]` → the recipient's slate.
6. `tx_lock_outputs` with the returned slate, then `finalize_tx`, then `post_tx` (`fluff` from the Dandelion switch).
7. `addAddress` with type `tor`.

Failure after step 6's lock: `cancel_tx` by slate id if finalize fails. If post fails, keep the transaction ("signed by both wallets, the node didn't take it") so it can be reposted or cancelled from Activity, as the HTTP send behaves today. Before step 6 nothing is locked or stored.

**Error codes, mapped to plain words (§6):**

| Cause | Code |
|---|---|
| SOCKS `0xF0`, `0xF2`, `0xF7`, or the connect timeout | `unreachable` |
| SOCKS `0xF6`, or the checksum | `invalid` |
| SOCKS `0xF3`, `0x01`, `0x06`, or a dropped stream | `broken` |
| SOCKS `0xF4`/`0xF5` | `auth` |
| HTTP not 200, or not JSON-RPC | `not_epic` |
| `foreign_api_version < 2`, or no V2/V3 | `too_old` |
| `receive_tx` error | `refused` (with the recipient's message) |
| `finalize`, `post` | `finalize`, `post` |

**Privacy notes** (the Help topic, short):

- Tor hides both wallets' IP addresses while they exchange the transaction. The finished transaction still goes to your node as usual.
- Your Tor address is permanent and comes from your wallet's key (it's also your payment-proof address). Anyone who has it can see when your wallet is online with Tor on.
- Epicbox, node checks and the built-in node don't use Tor.

## 7. Store and settings contract (so UI and backend can be built in parallel)

- `settingsStore`, per wallet: `tor_enabled: boolean` (missing = false). No schema bump if the store tolerates new keys; check `settingsStore.js`.
- `store.state.tor`: `{ enabled, state: 'off'|'starting'|'publishing'|'ready'|'failed', progress, onion: '' | '<56>.onion', error: '' | code, detail }`. The mutation is `tor`, fed by `tor-status` events.
- `walletService.setTorEnabled(bool)`, `walletService.torAddress()` (from `get_public_proof_address`), `walletService.sendOverTor(txData, onion, onStep)` → `{ok, slate} | {ok: false, code, detail}`.
- The onion is saved per wallet as `tor_onion` once known (it never changes). A start uses it at once and checks it against `get_public_proof_address` in the background (a different answer is saved and Tor restarted); without it the row says "Waiting for the wallet…" while the wallet answers (after a restore that call waits 1.5–2.5 min behind the scan).
- `window.api.tor.{start, stop, retry, foreign, onStatus}` in the preload. The contract test pins it.

### 7.1 As built (T2/T3, feat/tor-616-core, 21 Oct)

What the code does where the spec above left room, or where it differs:

- **Modules:** `src/shared/onion.js` (parseOnion, onionFromPubkeyHex, expandSeed, keyForTor), `torControl.js`, `torManager.js`, `torForeign.js` (the SOCKS5 + HTTP call and its allowlist), `torKeys.js` (the one-shot), `torSend.js` (the §5 send order, pure). `walletService.sendOverTor` wires `torSend` to the owner API and `window.api.tor.foreign`.
- **Error codes:** besides §5, `create` (init_send_tx failed, e.g. not enough funds; detail = the wallet's message) and `tor_off` (no tor, or not bootstrapped yet: the main process answers it, so the UI may call send without checking first). A failed `tx_lock_outputs` returns `finalize` (nothing to cancel). The SOCKS codes 0x04/0x05 map to `unreachable`, every other one to `broken`.
- **tor-foreign** answers `{ok: true, result: <the whole JSON-RPC envelope>}`; `torSend` reads `result.Ok` / `error` / `result.Err` from it. The page passes `isolation` (a SOCKS username, `[A-Za-z0-9_-]{1,64}`); `sendOverTor` makes one per send. Only while a wallet is unlocked.
- **tor-start** takes `{walletId, onion}`. The main process takes the dirs, network and listener port from settings.json and refuses a wallet other than the one whose password the session holds. A leftover recorded tor of that wallet is stopped first. The key file must be the onion's (seed format with that public key, else it's taken as already expanded and tor's ServiceID must equal the onion).
- **torkeys** is refused over `pty-start`: only the main process starts it. Its args always carry `--offline_mode` (checkPtyArgs), no `--no_tor`; its toml is deleted after the run.
- **Restarts:** `network` restarts after 5 s, 30 s, 2 min, then stays failed until Try again. A `CLOCK_SKEW` after the bootstrap only logs. The listener is checked every 15 s while ready.
- **Stop:** `stopOwnProcesses` (quit, signals, via shutdown.js) stops tor first; `shutdown.js` itself needed no change. The window reloading, crashing or closing stops it too. Wallet removal finds our recorded tor through `opts.tor` (processOwnership: role `tor`, dir = its torrc).

## 8. What stays CLI-side (notes for the epic-wallet maintainers)

1. `create_onion_service_sec_key_file` writes seed ‖ pubkey. Tor needs `ExpandedSecretKey` (SHA-512 of the seed, clamped), as grin-wallet writes it. Today tor publishes a different onion than `address` prints. **Breaks every 4.x Tor receive.**
2. Tor is started in a thread that `expect`s/`panic`s, with a 20 s timeout, no retry and no status the caller can read.
3. `ensure_running` treats anything on `socks_proxy_addr` (a system tor on 9050) as "running", so the wallet's own torrc and hidden service are never loaded, silently.
4. `owner_api` never sets `TOR_MANAGER` (onion sends from it go out without a proxy), has no `--no_tor`, and reads `use_tor_listener` from the shared toml.
5. `post_tx_tor` discards its result, so the `post_tx` fallback in `epicbox.rs` can never run. (The node-secret leak is fixed in 4.1.0.)
6. The listener reports the onion as `http://<onion>:<api_port>`, but the hidden service listens on port 80.
7. The tor path is hard-coded to `<exe dir>/tor/tor`. A `tor_path` in `[tor]` would help packagers.

## Risks

- **Windows antivirus may flag `tor.exe`.** The rig run shows whether Defender quarantines it.
- **Networks that block Tor** (no bridges in scope) end in the `network` error, which says so.
- **The Expert Bundle needs regular bumps** (six security releases May–Oct 2026). `--bump` makes it a one-command change. A monthly check belongs in the release checklist.
- **The `torkeys` one-shot depends on epic-wallet writing the key before its node check.** That holds for 4.1.0 (`init_tor_listener` runs first in `listen`). If a future wallet writes the right key format, `expandSeed` must not be applied twice: detect a file whose second half isn't the public key, and use it as-is.
- **macOS:** not built or tested in 6.1.6. The tor binaries would need hardened-runtime signing.
